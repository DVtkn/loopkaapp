# SECURITY.md — Политика безопасности и секретов проекта Loop

Данный документ определяет требования к управлению секретами, ключами и окружениями для обеспечения информационной безопасности приложения **Loop**.

---

## 1. Политика разделения секретов (Prod vs Dev)

Все секретные ключи, токены аутентификации и строки подключения **категорически запрещено** дублировать между Production и Development окружениями. В Production запрещено использовать предсказуемые значения по умолчанию или резервные подстроки (fallback strings).

| Имя переменной | Назначение | Обязательность в Production | Поведение при отсутствии в Prod |
| :--- | :--- | :--- | :--- |
| **`DATABASE_URL`** / **`NEON_DATABASE_URL`** | Строка подключения к PostgreSQL (Neon) | **ОБЯЗАТЕЛЬНО** | Сервер отказывается стартовать (`FATAL` вызов), предотвращает работу на временном диске. |
| **`JWT_SECRET`** | Секретный ключ подписи и проверки JWT-токенов | **ОБЯЗАТЕЛЬНО** | Сервер отказывается стартовать (`FATAL` вызов), предотвращает подделку токенов. |
| **`GROQ_API_KEY`** | Ключ доступа к API ИИ-психолога (Сова) | Рекомендуется | Работает в режиме безопасного локального движка правил. |
| **`GEMINI_API_KEY`** | Ключ доступа к Gemini API | Рекомендуется | Модули Gemini отключены или используют запасные шаблоны. |
| **`VAPID_PRIVATE_KEY`** | Приватный ключ Web Push уведомлений | Рекомендуется | Отключает отправку браузерных Push-уведомлений. |

## 2. Гарантии безопасности при смене JWT_SECRET

1. **Изоляция окружений**:
   - `/.env` (локальное dev-окружение): использует уникальный dev-ключ.
   - Cloud Run (Production): должен иметь собственный криптостойкий `JWT_SECRET` (сгенерированный например через `openssl rand -hex 32`).

2. **Аннулирование скомпрометированных сессий (Session Invalidation)**:
   - При установке или смене `JWT_SECRET` в производственной среде все токен-подписи, созданные старым или fallback-ключом (`loop_secret_fallback_12345`), становятся недействительными.
   - Метод `jwt.verify()` на сервере будет отклонять старые токены с ошибкой `JsonWebTokenError: invalid signature`, возвращая клиенту статус `HTTP 401 Unauthorized`.
   - Это гарантирует, что ни один токен, выданный во время работы с резервным ключом, не сможет быть использован для несанкционированного доступа.

## 3. Требования к развёртыванию новых инстансов (Checklist)

При деплое приложения на любой новый хостинг или стенд необходимо выполнить следующие шаги:

1. В панели управления хостингом (Cloud Run / Secret Manager) задать переменные:
   - `NODE_ENV=production`
   - `DATABASE_URL="postgresql://..."`
   - `JWT_SECRET="<уникальный_64_символьный_hex_ключ>"`
2. Убедиться, что сервер стартует без логов вида `FATAL: В production-режиме обязательно наличие переменной...`.
3. Убедиться, что логи не содержат `Using fallback (NOT safe for production)`.
