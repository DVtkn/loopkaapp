# Безопасность и управление секретами

## 1. Политика изоляции секретов (Prod vs Dev)

Безопасность личных данных пары — абсолютный приоритет Loop. Все секретные ключи, токены и параметры доступа строго изолированы между средами разработки и эксплуатации.

В продакшн-среде действует правило **Fail-Fast**: если хотя бы один критический секрет не настроен, сервер завершает работу с фатальной ошибкой ещё на этапе инициализации, защищая данные от утечки или записи на незащищённый временный диск.

| Переменная окружения | Назначение | Обязательность в Production | Поведение при отсутствии в Prod |
| :--- | :--- | :--- | :--- |
| `DATABASE_URL` / `NEON_DATABASE_URL` | Строка подключения к PostgreSQL (Neon) с SSL. | **Обязательно** | Запуск немедленно блокируется (`FATAL`), предотвращая работу на временном локальном диске. |
| `JWT_SECRET` | Криптографический ключ для подписи и валидации сессионных JWT-токенов. | **Обязательно** | Запуск блокируется (`FATAL`), предотвращая подделку сессий с дефолтным ключом. |
| `GROQ_API_KEY` | Ключ доступа к модели ИИ-психолога «Сова». | Рекомендуется | При отсутствии сервер мягко переключается на встроенный движок правил `psychologyEngine`. |
| `GEMINI_API_KEY` | Ключ доступа к дополнительным функциям Gemini. | Опционально | Дополнительные модули отключаются или используют запасные шаблоны. |
| `VAPID_PRIVATE_KEY` | Приватный ключ для отправки Web Push уведомлений в браузеры. | Рекомендуется | Браузерные push-уведомления отключаются, доставка касаний работает через SSE. |

## 2. Ротация JWT_SECRET и инвалидация сессий

При смене или компрометации секрета `JWT_SECRET` система гарантирует автоматическую защиту учётных записей:

1. **Немедленная инвалидация старых сессий**:  
   При обновлении `JWT_SECRET` на хостинге все ранее выданные токены теряют валидность. Метод проверки `jwt.verify()` на сервере отклоняет их с кодом `JsonWebTokenError: invalid signature` и возвращает статус `HTTP 401 Unauthorized`.
2. **Безопасный разрыв подозрительных подключений**:  
   Ни один пользователь или злоумышленник не сможет продолжать работу со старыми токенами без повторного ввода пароля.

## 3. Криптография паролей и защита от атак

- **Хеширование паролей**: выполняется с использованием библиотеки `bcryptjs` с фактором сложности 10 раундов. Открытые пароли никогда не сохраняются в базе данных и не выводятся в лог-файлы.
- **Защита от перебора (Brute-Force Protection)**: эндпоинты аутентификации защищены rate-лимитером `loginLimiter`, блокирующим подбор паролей (не более 5 неудачных попыток за 15-минутный интервал).
- **Защита от тайминг-атак**: проверка паролей выполняется с фиксированным временем ответа независимо от того, существует ли логин в базе данных.
- **Защита от IDOR (Insecure Direct Object Reference)**: доступ к любым данным пары проверяется middleware `requirePairOwnership`, исключающим чтение чужих записей.

## 4. Чек-лист развёртывания нового стенда

Перед запуском инстанса в Cloud Run или на виртуальном сервере:

1. В Secret Manager или панели управления переменными задать `NODE_ENV=production`.
2. Задать криптостойкий `JWT_SECRET` (рекомендуется сгенерировать 64-символьную hex-последовательность с помощью команды `openssl rand -hex 32`).
3. Указать боевую строку `DATABASE_URL` с параметром `sslmode=require`.
4. Проверить логи старта: в них должно присутствовать сообщение об успешной инициализации PostgreSQL и отсутствовать предупреждения `Using fallback`.
