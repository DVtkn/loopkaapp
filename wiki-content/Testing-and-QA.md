# Тестирование и контроль качества

## 1. Философия качества и Definition of Done (DoD)

В проекте Loop действует строгое правило: **функциональность важнее декораций**. Ни одна задача не считается выполненной, если она не прошла сквозную проверку.

### Чек-лист приёмки (DoD):
1. **End-to-End функциональность**: каждый интерактивный элемент (кнопка, тап, свайп, long-press) имеет рабочий обработчик, выполняющий сохранение или чтение данных на сервере.
2. **Двусторонняя проверка P0-сценариев**: поскольку Loop — продукт для двоих, любые механики пары проверяются с точки зрения обоих аккаунтов (пользователь А инициирует → пользователь Б видит обновление состояния без рассинхронизации).
3. **Контроль регрессий визуальных токенов**: перед закрытием задачи обязательно проверяется сохранение цветных подложек иконок, отсутствие обрезания строк (`truncate`) и отсутствие случайных дефолтных рамок UI-библиотек.
4. **Валидация типов и сборка**: обязательное успешное выполнение `npm run lint` и `npm run build`.

## 2. Методология верификации: Red / Green цикл

Для критических участков бэкенда (связывание пары, финансовые или геймификационные механики) используется принцип обязательной проверки отказов:
- **Red-фаза**: проверка того, что тест гарантированно падает при намеренном внесении дефекта (например, попытка связать пользователя с самим собой или передать поддельный `level: 999` с клиента).
- **Green-фаза**: проверка успешного и безопасного прохождения сценария в эталонной реализации с сохранением сырых логов выполнения.

## 3. Набор интеграционных тестов

Скрипты тестирования расположены в каталоге `tests/` и запускаются через `tsx`:

| Файл теста | Назначение |
| :--- | :--- |
| `tests/run-integration-full.ts` | Сквозной интеграционный прогон: регистрация двух пользователей, отправка и принятие заявки в пару, сохранение данных, отправка сообщений и проверка SSE-касаний. |
| `tests/test-prod-db-failfast.ts` | Проверка поведения сервера в режиме `NODE_ENV=production` без переменной `DATABASE_URL` (сервер обязан завершить работу с ошибкой `FATAL`). |
| `tests/test-dev-db-fallback.ts` | Проверка мягкого запуска на локальном хранилище `/data/db_store.json` в dev-режиме при отсутствии базы данных. |
| `tests/test-sync-vuln.ts` | Проверка защиты от инъекции уровня: сервер обязан отсекать клиентские поля уровня и рассчитывать XP самостоятельно. |

Команда запуска полного пакета:

```bash
npx tsx tests/run-integration-full.ts
```

## 4. Известные пробелы и открытые пункты

Мы честно фиксируем текущие ограничения тестового контура:

1. **Frontend E2E тестирование в CI/CD**:
   - Написаны базовые сценарии `e2e/loop.spec.ts` для Playwright, однако запуск браузерных тестов пока не интегрирован в пайплайн автоматической сборки GitHub Actions.
2. **Интеграционное тестирование Web Push (VAPID)**:
   - Доставка сообщений на реальные мобильные устройства через Service Worker протестирована вручную, но отсутствует мок-сьют для автоматической верификации доставки push-нотификаций при регрессиях.
3. **Live Groq AI Verification Gate**:
   - В тестах используется локальный движок `psychologyEngine.ts`. Требуется регулярный мониторинг времени ответа и структуры ответов внешней модели Llama на живом API Groq.

*Подробнее о шагах по устранению пробелов см. страницу [План развития (Roadmap)](Roadmap).*
